## Project Abstract

Smart Parking Occupancy Analytics is a production-grade, real-time stream processing system designed to ingest, validate, process, and visualise parking sensor events from multiple locations across Bengaluru. The system demonstrates the full lifecycle of a modern event-driven architecture: synthetic sensor events are generated by a configurable simulator, published to Apache Kafka topics, consumed and processed by Apache Spark Structured Streaming, stored in InfluxDB time-series database, and rendered in live Grafana dashboards — all within a fully containerised local environment.

The project addresses a genuine urban computing challenge: city planners and parking operators lack real-time insight into occupancy patterns across distributed sensor networks. Traditional batch ETL pipelines introduce latency measured in hours, rendering the data unsuitable for operational decisions such as dynamic pricing, guidance signage control, or congestion mitigation. This system reduces end-to-end latency to sub-second levels under normal operating loads, enabling truly reactive analytics.

From an academic perspective, the project serves as a comprehensive practical exploration of stream processing theory. Concepts including event-time semantics, watermark-based late-data handling, stateful aggregations, fault-tolerant checkpointing, exactly-once delivery simulation, tumbling and sliding window analytics, and dead-letter queue routing are all implemented and observable in a running system. Each component has been designed to be inspectable, with structured logging and Spark UI metrics surfaced at every stage.

The architecture deliberately mirrors industry-standard deployments used by organisations such as Uber (Kafka + Flink), LinkedIn (origin of Kafka), and Databricks (Spark). By reproducing a production-quality pipeline at academic scale, this project provides a foundation for understanding how large-scale streaming systems are designed, operated, and debugged in practice.

## Starting the System

```bash
# 1. Start infrastructure services (Kafka, InfluxDB, Grafana)
docker compose up -d

# 2. Verify all services are healthy
python scripts/health_check.py

# 3. Start the parking sensor simulator (normal mode, 50 events/sec)
python -m simulator.main --mode normal --rate 50

# 4. Start Spark stream processing (open a NEW terminal, activate venv first)
python -m streaming.main --watermark "2 minutes" --trigger "10 seconds"

# 5. Open Grafana dashboard
#    URL:      http://localhost:3000
#    Username: admin
#    Password: parking123
```

> **Tip:** Run the simulator and streaming engine in separate terminal windows so you can monitor their logs independently.

## Simulator Modes

The sensor simulator supports multiple operating modes to exercise different system behaviours:

```bash
# Normal operation — steady 50 events/sec across all lots
python -m simulator.main --mode normal

# High load — 500 events/sec to test throughput ceiling
python -m simulator.main --mode high_load

# Peak hour — 100 events/sec with realistic morning/evening surge patterns
python -m simulator.main --mode peak_hour

# Fault injection — includes duplicates and late-arriving events
python -m simulator.main --mode fault_injection

# Benchmark — reproducible seed, 1000 events/sec, fixed duration
python -m simulator.main --mode benchmark

# Custom rate and duration
python -m simulator.main --rate 100 --duration 60   # 100/sec for 60 seconds

# Dry run — generate and validate events without sending to Kafka
python -m simulator.main --dry-run
```

### Mode Summary

| Mode | Rate | Special Behaviour |
|------|------|------------------|
| `normal` | 50 /sec | Baseline realistic traffic |
| `high_load` | 500 /sec | Stress test; may reveal backpressure |
| `peak_hour` | 100 /sec | Time-of-day occupancy patterns |
| `fault_injection` | 50 /sec | ~5% duplicates, ~3% late events (up to 10 min) |
| `benchmark` | 1000 /sec | Fixed random seed for reproducibility |

## Kafka Topics

| Topic | Partitions | Retention | Purpose |
|-------|-----------|-----------|---------|
| `parking.sensor.events` | 8 | 7 days | Raw sensor events from simulator; partitioned by `lot_id` |
| `parking.sensor.events.dlq` | 1 | 30 days | Dead-letter queue for invalid/malformed events |
| `parking.aggregated.occupancy` | 4 | 1 day | Windowed occupancy aggregations output from Spark |

Partition key for `parking.sensor.events` is `lot_id`, ensuring all events from the same lot are processed in order within a single Spark task.

## Stream Processing Concepts Demonstrated

This project provides hands-on implementation of the following stream processing concepts:

1. **Event-time processing** — using `event_timestamp` embedded in each message, not Kafka ingestion time
2. **Watermarks** — bounding late-data state with a configurable maximum lateness threshold
3. **Tumbling windows** — non-overlapping 1-minute windows for discrete occupancy snapshots
4. **Sliding windows** — 5-minute windows sliding every 1 minute for smoothed trend lines
5. **Stateful aggregation** — maintaining per-lot running state across micro-batches
6. **`flatMapGroupsWithState`** — arbitrary stateful transformations with explicit state lifecycle
7. **`GroupState` timeout** — automatic state expiry for inactive lots
8. **Deduplication** — `dropDuplicates` with watermark to prevent double-counting
9. **Schema validation** — enforcing `StructType` at ingestion boundary
10. **Dead-letter queues (DLQ)** — routing invalid events to a separate topic for auditing
11. **Kafka source integration** — `readStream` with Kafka broker, topic, and offset configuration
12. **Kafka sink integration** — `writeStream` publishing aggregations back to Kafka
13. **InfluxDB sink** — `foreachBatch` writing to time-series database
14. **Checkpointing** — persisting Spark offsets, state, and watermark for crash recovery
15. **Micro-batch processing model** — trigger intervals and their latency/throughput trade-offs
16. **Output modes** — `update`, `append`, and `complete` modes and when each applies
17. **Backpressure** — Spark's rate limiting when consumer lags behind producer
18. **At-least-once delivery** — Kafka producer `acks=all` and consumer offset management
19. **Exactly-once semantics** — simulated via deduplication within watermark window
20. **Fault injection** — simulator generating duplicates and late-arriving events for testing
21. **Late event handling** — events with timestamps older than watermark threshold
22. **Partition-key design** — `lot_id` as Kafka partition key for ordered processing
23. **KRaft mode** — Kafka without ZooKeeper, using internal Raft consensus
24. **Consumer group coordination** — Spark's internal consumer group management

## Fault Tolerance

This system is designed to recover automatically from component failures without data loss.

### Testing Spark Restart and Checkpoint Recovery

1. Start all services and verify data is flowing to Grafana.
2. In the Spark terminal, press **Ctrl+C** to kill the streaming engine.
3. Wait 30 seconds (observe the simulator continues publishing to Kafka — no events are lost).
4. Restart Spark:
   ```bash
   python -m streaming.main --watermark "2 minutes" --trigger "10 seconds"
   ```
5. Observe the startup logs — Spark reads the checkpoint and resumes from the **exact Kafka offset** where it stopped.
6. No gap should appear in Grafana metrics.

For detailed fault tolerance documentation including all failure experiments, see [docs/fault_tolerance.md](docs/fault_tolerance.md).
